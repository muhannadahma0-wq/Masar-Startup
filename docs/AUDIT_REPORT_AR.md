# تقرير مراجعة Masar Startup قبل النشر

**تاريخ المراجعة:** 17 أكتوبر 2026  
**النطاق:** مقارنة شجرة المصدر بالخطة المعدّلة، وفحص الإضافات والملفات والاختبارات المتاحة محليًا.  
**قرار الإصدار:** **لا تُنشر هذه النسخة للإنتاج بعد.** لم يُرفع شيء إلى GitHub ولم تتغير أي خدمة على Render أثناء هذه المراجعة.

## ما تم التحقق منه محليًا

- التطبيق منظّم كتطبيق Next.js App Router واحد، مع واجهات API بخادم Node.js وPrisma ومخطط PostgreSQL.
- يوجد 32 ملف مسار API تحت `src/app/api/v1`، و12 شاشة رئيسية منفصلة.
- محرك الأهلية يعيد أحكامًا حتمية ثلاثية القيم؛ مراجعة الذكاء الاصطناعي لا تتخذ قرار الأهلية.
- توجد شبكة LangGraph.js تحتوي على 20 دور مراجعة متخصصًا، وقيود للتوازي والمهل، وحارس اقتباسات. هذه استدعاءات متخصصة للنموذج وليست 20 نموذجًا مدرّبًا مستقلًا.
- ملفات إعداد Render وDocker وCompose و`package.json` صالحة نحويًا.
- فحص محلل TypeScript/TSX لـ **143 ملفًا** لم يجد أخطاء نحوية.
- اختبارات `tests/*.test.mjs`: **8/8 ناجحة** بعد إضافة اختبارات ساكنة للبروفايل وإخفاء البيانات الشخصية.
- `scripts/verify-release.mjs` و`git diff --check` ناجحان.

**حدّ هذا التحقق:** هذه فحوص بنيوية وساكنة، وليست دليلًا على نجاح TypeScript typecheck أو بناء Next.js أو تشغيل التطبيق مع PostgreSQL أو استدعاء نموذج حي.

## إصلاحات أُجريت خلال المراجعة

1. **حفظ قوائم ملف الشركة:** مخطط Zod كان يمنع قيمًا مصفوفية مثل القطاعات واللغات وطرق استلام التمويل؛ عُدّل ليقبل القيم البدائية والمصفوفات البدائية.
2. **حفظ المؤسسين:** أُضيف دعم حفظ قائمة المؤسسين في `PUT /profile` داخل معاملة واحدة، مع فرض وجود مؤسس أساسي واحد بالضبط. واجهة الملف ترسل تغييرات الأسماء والإقامة والجنسية واختيار المؤسس الأساسي، مع إبقاء سجل المؤسس الأساسي متوافقًا مع حقول الملف التي يعتمد عليها محرك المطابقة.
3. **خصوصية مراجعة العرض:** أصبح نص عنوان الشريحة ونصها يمران عبر حارس إخفاء البيانات الشخصية قبل إرسالهما لوكلاء المراجعة؛ وما زال الاقتباس المعروض يحتاج إلى اجتياز حارس المطابقة مع الشريحة الأصلية.
4. **وضوح الإشعارات:** عُدّلت تعليقات التنفيذ لتوضح أن نجاح حفظ الإشعار يعني إنشاء إشعار داخل التطبيق، وليس إرسال بريد إلكتروني.
5. **أخطاء ترجمة TypeScript التي أمكن كشفها دون الاعتماديات:** أُضيف نوع `ReadinessLevel` المفقود، وأُصلحت تمريرات اللغة إلى أقسام الجاهزية والفجوات ومقارنة النسخ. استُبعد مجلد المثال القديم `examples/` من فحص TypeScript للمشروع لأنه يخص خادم Socket.IO تجريبيًا ولا يدخل في بنية تطبيق Next.js الحالية.

## فجوات تمنع اعتبار المشروع مكتملًا وفق الخطة

| الأولوية | الحالة | التفاصيل |
|---|---|---|
| مانع نشر | غير متحقق | تعذّر تثبيت الاعتماديات من npm بسبب فشل الاتصال بسجل الحزم؛ لذلك لم يُشغّل `npm run typecheck` أو `npm run lint` أو `npm run build` فعليًا. |
| مانع نشر | ناقص | لا يوجد `package-lock.json`، ما يجعل تثبيت الاعتماديات في البناء غير مثبت بإصدارات متكررة. |
| مانع إنتاج | يحتاج قرارًا | لا توجد مجلدات `prisma/migrations` بعد. إعداد Render وDocker ينفذان `prisma db push` عند بدء التطبيق؛ يجب اعتماد ترحيلات مراجعة/نسخ احتياطي قبل بيانات المستخدمين بدل الاعتماد على تغيير المخطط كل تشغيل. |
| مانع المنتج الأساسي | غير متحقق | بيانات seed المعروضة توضيحية وخيالية وروابطها من `demo.masar.example`؛ ليست 50 فرصة حقيقية جرى التحقق من مصادرها الرسمية. قاعدة البيانات الجديدة على Render تبدأ فارغة ما لم تُجهز بيانات فعلية. |
| مانع متطلب Must | ناقص | الإشعارات داخل التطبيق فقط. لا توجد خدمة إرسال بريد مدمجة، لذا تنبيهات البريد وتغييرات الفرص المطلوبة في الخطة غير مكتملة. |
| مانع خصوصية | ناقص | لا توجد آلية كاملة لحذف حساب المستخدم وملفاته الأصلية، ولا سياسة/مهمة تنظيف تحقق الاحتفاظ الافتراضي 90 يومًا. حذف سجل قاعدة البيانات وحده لا يحذف الملفات المحفوظة على القرص. |
| مانع رفع ملفات حقيقي | ناقص | تخزين العروض محلي داخل `storage/decks`؛ إعداد Render لا يوفر قرصًا دائمًا أو مخزن كائنات خاصًا. نظام Render العادي لا يكفي لحفظ عروض المستخدمين بصورة دائمة. |
| أمان | يحتاج تقوية واختبار | حارس SSRF يحظر كثيرًا من عناوين IP المحلية، لكنه لا يتحقق من عناوين DNS التي يحل إليها اسم نطاق، ويحتاج إلى تغطية أدق لعناوين IPv6 المعيّنة إلى IPv4. لا تستخدم ميزة جلب الروابط للإنتاج قبل تقويتها واختبار إعادة التوجيه وDNS rebinding. |
| تحقق أكاديمي | ناقص | توجد سكربتات فحص مثل `scripts/check-engine.ts` و`check-auth.ts` و`check-decks.ts` وغيرها، لكنها لم تُشغّل في هذه البيئة لغياب الاعتماديات/قاعدة البيانات، كما أن `test:smoke` يشغّل الفحوص الساكنة فقط. لا يوجد مجلد تقييم `eval/` لإعادة تشغيل E1/E3/E5 كما تصف الخطة. |
| توثيق/حوكمة | ناقص | لا تظهر في الحزمة ملفات `THIRD_PARTY_NOTICES` أو سياسة المراجعين المطلوبة في الخطة. |
| تهيئة بيانات | جزئي | واجهة المستندات والمتتبع وحالة الجاهزية والمطابقات و«ماذا لو» موجودة في المصدر، لكن يجب إجراء اختبار تكاملي على قاعدة PostgreSQL فعلية قبل الادعاء أن تدفقات المستخدم تعمل من البداية للنهاية. |
| ترجمة | جزئي | أُضيفت ترجمات ورسائل احتياطية عربية/إنجليزية في عدة مسارات، لكن لا يوجد اختبار متصفح كامل للواجهتين RTL/LTR، وتبقى عناوين/أوصاف الفرص الرسمية بلغتها المصدرية عمدًا. |

## مطابقة النطاق وتعارضه

تطلب الخطة المعدّلة الأصلية تنفيذ TypeScript/PostgreSQL وتذكر صراحةً عدم إضافة إطار وكلاء متعددين. بينما طلب لاحق في المحادثة إضافة 20 دورًا باستخدام إطار تنسيق، لذا أضيفت مراجعة LangGraph منفصلة دون ربطها بحكم الأهلية. ينبغي اعتبار هذا **تغيير نطاق واعيًا** وتوثيقه في قرار المشروع النهائي بدل وصفه بأنه مطابق حرفيًا للخطة الأصلية.

## بوابات القبول قبل GitHub / Render

1. تثبيت الاعتماديات بنجاح وإنشاء lockfile موثوق، ثم تشغيل typecheck وlint وbuild.
2. تنفيذ اختبارات قاعدة البيانات والمسارات وملكية الموارد على PostgreSQL نظيف، وتوثيق النتائج بما فيها الحالات الثلاث للأهلية.
3. اعتماد استراتيجية migrations والنسخ الاحتياطي؛ عدم نشر قاعدة إنتاج مع `db push` تلقائي لكل تشغيل دون مراجعة.
4. جمع 50 فرصة حقيقية على الأقل بروابط رسمية وشروط/أدلة وتاريخ تحقق ومراجعة بشرية؛ فصل بيانات العرض التجريبي بوضوح.
5. إضافة البريد الإلكتروني أو تغيير تعريف المتطلب رسميًا إلى إشعارات داخل التطبيق فقط.
6. إضافة حذف الحساب والملفات وسياسة retention فعلية وتخزين خاص دائم للعروض، ثم اختبار الاسترجاع.
7. تقوية SSRF، وإكمال `eval/` والتوثيق المطلوب، ثم مراجعة RTL/LTR كاملة.
8. بعد نجاح هذه البوابات فقط، إنشاء خدمة Render جديدة معزولة وعدم المساس بالخدمات السابقة قبل التحقق من صحة الإطلاق الجديد.
